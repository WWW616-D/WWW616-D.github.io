第七章

链接的本质：把多个.o目标文件合并成一个可执行文件，核心工作是符号解析（解决谁定义了哪个符号）和重定位（把相对偏移改成绝对虚拟地址）。

两种链接方式：静态链接（.a）在编译时把库代码复制进可执行文件；动态链接（.so）在加载/运行时才解析地址，通过GOT和PLT实现位置无关代码和延迟绑定。

关键细节：静态库链接时顺序敏感（被依赖的库要放后面）；动态库通过LD_PRELOAD可以实现库打桩（用自己的函数替换系统库函数）。

什么是缺页异常？

一句话解释：程序想访问的内存数据，当前不在物理内存里，需要从磁盘（或交换区）重新加载进来。

缺页异常的完整处理流程（和第八讲完美对应）

当CPU访问一个虚拟地址，而对应的物理页不在内存中时，硬件会触发缺页异常（属于"故障/Fault"类型），跳转到内核的缺页处理程序：

⚠️ 关键认知（第八讲重点）：故障（Fault）的返回地址是当前指令，而不是下一条。因为缺页异常修复后，需要把刚才失败的访问重新执行一遍。

缺页异常是程序能遇到的最慢操作之一：

操作 耗时（纳秒） 相对比例
CPU缓存命中 ~1 ns 1x
物理内存访问 ~100 ns 100x
缺页异常（从磁盘读取） ~10,000,000 ns (10ms) 10,000,000x

一次缺页异常的时间，等于1000万次内存访问。所以操作系统会极力避免缺页异常，深度学习框架也会拼命预分配显存来绕过它。

🚀 深度学习的直接关联（重点！）

1. 大模型加载时的"慢启动"

当你用 torch.load() 加载一个 70GB 的模型权重时，你注意到的第一件事是加载慢。但更深层的是：

  • 如果系统内存不够，会把模型的一部分交换到磁盘（swap）上。
  • 训练时，访问到某个权重张量，发现它在swap里 → 触发缺页异常 → 从磁盘读回 → 训练突然卡住一会儿。
  • 症状：loss正常下降，但每隔几分钟突然有个尖刺（latency spike）。
    解决方案：mlock() 或 torch.cuda.set_pin_memory()，把关键数据锁定在物理内存中，禁止被换出。

2. DataLoader 的 pin_memory=True 的真正原理

你在PyTorch里设 pin_memory=True 时，其实是告诉操作系统：

“这块数据我很常用，不要把它交换到磁盘上去，就钉在物理内存里。”

底层调用的是 mlock 或 cudaHostAlloc 这样的系统调用。本质上是在减少缺页异常，提高CPU→GPU的数据传输速度。

3. GPU显存溢出时的"隐形缺页"

NVIDIA GPU从Volta架构开始支持Unified Memory（统一内存），即CPU和GPU共享同一块虚拟地址空间。
当你分配的显存超过GPU物理显存时：

  • CUDA驱动会自动在GPU显存↔系统内存之间交换数据。
  • 访问不在GPU上的数据 → 触发GPU缺页异常 → 数据从系统内存搬过来 → 性能陡降。
  • 症状：训练速度突然从1000 iter/s掉到50 iter/s，GPU利用率掉到0%。
    对策：关闭统一内存，使用显式 cudaMemcpy，手动控制数据在哪，避免隐形缺页。

4. 检查你的训练环境

在训练大模型前，用命令确认：

  • min_flt（次缺页）：页已经在内存，只是页表没映射，很快，影响不大。
  • maj_flt（主缺页）：需要从磁盘读取，非常致命。如果这个数字在训练中不断增长，你的训练速度会被拉低几个数量级。

一句话终极总结

缺页异常 = 程序访问了一块不在物理内存中的数据，被迫去磁盘取回来的"卡顿"。在深度学习中，它表现为显存溢出后的隐性降速、数据加载的尖刺延迟，以及模型加载时的漫长等待。所有的内存钉锁（pin_memory）、内存池（memory pool）、预分配策略，归根结底都是在和缺页异常作斗争。

📚 CSAPP 第八讲：异常控制流（ECF）与进程管理 · 极简笔记

1. 什么是异常控制流（ECF）？

CPU正常情况下是按顺序执行指令的，但遇到特殊事件必须“岔开”去处理。这种“岔开”就是异常控制流。

异常的类型（记住这四个词）

  • 中断（Interrupt）：来自外部（硬件）。比如键盘敲了一下、网卡来了个数据包。异步发生。
  • 陷阱（Trap）：主动为之（程序故意的）。最常见的就是系统调用（如 read、fork）。同步发生。
  • 故障（Fault）：可能修复的错误。最常见的是缺页异常。如果修复成功，重新执行该指令；如果修复失败，变成下面这个。
  • 终止（Abort）：致命的硬件错误。直接崩溃，不返回。

2. 进程的三个“幻觉”

进程 = 运行中的程序。操作系统通过进程制造了两个幻觉，让你觉得电脑是你一个人的：

  1. 独享CPU：虽然单核同时只能跑一个进程，但通过快速切换（上下文切换），让你觉得它在同时运行。
  2. 独享内存：每个进程都觉得自己拥有整块内存（私有的地址空间）。

3. 进程管理的“四大金刚”（重点背诵）

这两页的核心就是下面的四个操作，贯穿了整个操作系统：

① 生娃：fork()

  • 作用：创建一个子进程（复制当前进程）。
  • 诡异之处：一次调用，两次返回。
    • 父进程返回：子进程的 PID（大于0）。
    • 子进程返回：0。
  • 记忆点：子进程从 fork 返回处开始执行，代码一模一样，但各走各的分支。

② 自杀：exit()

  • 作用：终止当前进程。
  • 诡异之处：一次调用，无返回（调用了就回不来了，进程直接消失）。

③ 收尸：wait() 或 waitpid()

  • 作用：父进程等待子进程结束，回收其资源（读取出殡状态）。
  • 如果不收尸：子进程死了但父进程不管，就会变成僵尸进程（Zombie），占着茅坑（PID）不拉屎。
  • 如果父进程先死：子进程变成孤儿，被 init 进程（PID=1）收养。

④ 换脑：execve()

  • 作用：在当前进程中，加载一个全新的程序（比如把 bash 变成 ls）。
  • 诡异之处：一次调用，无返回（一旦成功，原来的代码就没了，被新代码覆盖）。
  • 与 fork 的组合技：
    • Shell 启动程序 = fork() （复印自己） + execve()（子进程换脑） + waitpid()（等着收尸）。

4. 对深度学习的实战映射（快速回顾）

把上面四个概念套进你每天做的事情里，就全通了：

  • 当你启动训练：bash 先 fork，然后子进程 execve 变成 python 解释器，跑你的 train.py。
  • 当你开启 num_workers：你的主进程 fork 出多个子进程去并行处理数据。
  • 当你按 Ctrl+C：系统发出中断信号，你的进程收到信号后执行 exit。
  • 当显存报错 OOM：操作系统觉得你太吃内存了，可能直接发信号把你进程给 kill 了（终结）。
  • 当你发现显存没释放（孤儿）：因为你的父进程（Jupyter）崩溃了，但你 fork 出来的 DataLoader 子进程还在后台跑着。

制造阻塞，取消阻塞的方法

printf、sprintf、malloc 在信号处理函数里不安全,是因为它们内部使用了全局锁或操作了全局数据结构,而信号处理函数可能在主程序正持有这些锁或正在修改这些数据时被调用,导致死锁或数据损坏。 正确的做法是：信号处理函数里只设置标志位,所有复杂操作(打印、分配内存、保存模型)放到主循环里完成。

三大信号处理代码编写纪律

第一大纪律：做“最少”的事（G0 + G1）

  • G0（保持简单）：信号处理函数里只做最基本的事，比如设置一个全局标志位，然后立刻返回。把复杂操作（比如打印、保存模型）留给主循环去处理。
  • G1（只调用安全函数）：你只能调用系统允许的“异步信号安全”函数（如 write、read），绝对不能碰 printf、malloc 这些会加锁或操作共享数据的函数。

第二大纪律：保护“全局变量”（G3 + G4 + G5）

这几条都是为了防止你的程序出现意想不到的数据错乱或死锁。

  • G3（临时屏蔽信号）：当你在主程序里操作全局数据时，先通过 sigprocmask 暂时屏蔽信号，保证操作原子性，不被信号中断。
  • G4（使用 volatile 关键字）：告诉编译器：“这个变量会被信号处理函数偷偷修改，别把它优化到寄存器里，每次都要去内存读最新值。”
  • G5（使用 sig_atomic_t 类型）：专门用来声明全局标志位（比如 interrupted），保证读写操作是原子的，不会被信号中断打断。

第三大纪律：保存“现场”（G2）

  • G2（保存和恢复 errno）：系统调用失败时会设置 errno。如果在信号处理函数里调用了系统调用（比如 write），它会修改 errno。你需要在函数入口保存它，在出口恢复它，保证不污染主程序原本的错误信息。
